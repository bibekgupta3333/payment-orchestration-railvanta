# Black-box M1 tests

Run `pnpm test:e2e` from the repository root after installing dependencies and Chromium (`pnpm --filter @railvanta/e2e exec playwright install chromium`). Go with CGO/C compiler support and Python 3 are required.

Global setup builds the Go binary, creates a fresh temporary SQLite database, generates ephemeral credentials, and starts the API and Next.js on free loopback ports. API specs also use Next.js to verify the `/v1` proxy. Teardown stops both process groups and deletes only the harness temporary directory. No existing local database is used.

The authenticated loopback control server belongs to the test harness, not the application. `restartApi()` sends SIGTERM; `killApi()` sends SIGKILL. Both reopen the same database. A durability fixture inserts an unseeded payment method while the API is stopped, so startup reseeding cannot mask lost data. The checksum test prepares controlled corruption while the API is stopped, observes startup failure, restores the fixture, and restarts the API. Test assertions use HTTP or the browser, with one exception: `inspectPayment()` reads (read-only SQLite URI) the rows the API deliberately hides — provider idempotency keys, `mock_provider_charges` and outbox rows for one payment — so dispatch specs can prove one charge per key. `redeliverDispatch()` re-queues a payment's `payment.dispatch` outbox row while the API runs, simulating a lost completion. `seedCreatedPayment()` stops the API, inserts a payment that stays `created` (its dispatch command is due in an hour) and restarts, so cancellation specs are deterministic; `inspectPayment()` also returns the audit `transitions`. The harness sets fast dispatcher timing (`DISPATCHER_POLL_INTERVAL=50ms`, `DISPATCHER_LEASE=2s`, `MOCK_TIMEOUT_DELAY=200ms`, `RECOVERY_BASE_BACKOFF=100ms`, `RECOVERY_MAX_BACKOFF=500ms`) and a long `MOCK_DELAYED_SUCCESS_DELAY=8s` so a spec can kill the API while an attempt is `submitted`. Scenario payment methods are seeded with stable IDs (`fixtures.successMethod`, `declineMethod`, `delayedSuccessMethod`, `timeoutBeforeExecutionMethod`, `timeoutAfterSuccessMethod`, `outageMethod`).

**Container mode.** With `E2E_BASE_URL` set (for example `http://localhost:3000`), global setup skips building and booting native processes and uses the running `docker compose` stack at one origin (start it with `docker-compose.e2e.yml` layered on `docker-compose.yml` for the fast dispatcher timings; honor `COMPOSE_PROJECT_NAME`/`COMPOSE_FILE`). Credentials are provisioned with `railvanta-api seed-demo` and cached per Compose project. The control server is implemented in `support/containers.ts` with `docker compose kill/stop/start`, `compose exec` and read-only/stopped-API access to the data volume through a pinned python helper container. `e2e/ops/*.spec.ts` (backup/restore, non-root, private health, container kill) run only in this mode. `api/scaffold.spec.ts` "private readiness" is native-only (the container health listener is private; the same facts are asserted by `ops/container-runtime.spec.ts`). Use a fresh volume (`docker compose down -v`) when first starting a stack.

The temporary state file contains generated secrets and is created with mode `0600`. Do not copy it into reports or commit it. Tests use one worker and no retries because lifecycle tests deliberately restart shared processes. API responses are checked against the OpenAPI schemas. Payment execution is outside M1; a valid payment intent must currently return the documented `501` unavailable response.
