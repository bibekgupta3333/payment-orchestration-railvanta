# Case study: not losing track of money when the response is lost

A short technical account of what Railvanta is, the few design choices that carry the weight, what the demos prove, and what was learned (WBS 5.4.8). It is a sandbox with a deterministic mock provider; no real funds move. Limits are in [known-limitations.md](known-limitations.md) and numbers in [measurements.md](measurements.md).

## The problem

A payment orchestrator sits between a merchant and one or more providers. The hard case is not the decline or the clean success. It is the request that times out after the provider already took the money: the caller sees an error, a naive retry charges twice, and a naive "failed" status disagrees with the provider's books. Railvanta is built so that this case ends with exactly one charge, exactly one balanced ledger journal, and a payment whose recorded state matches what the provider did.

## Design choices that matter

1. **Idempotent acceptance.** `POST /v1/payments` requires an `Idempotency-Key`. One transaction inserts the payment, its first audit transition and the dispatch command, keyed so a repeat with the same key and body replays the stored response byte for byte, and a repeat with a different body gets 409. Concurrent duplicates collapse to one payment (measured: 1 payment, 1 charge and 1 journal at 2, 8 and 32 concurrent requests; see [measurements.md](measurements.md)).
2. **Transactional outbox.** Acceptance never calls a provider. It writes a `payment.dispatch` row in the same transaction as the payment, and a leased dispatcher claims it. A crash between "accepted" and "dispatched" leaves a durable command; an expired lease is reclaimed. Delivery is at least once, so every consumer has to be safe to repeat.
3. **Provider I/O outside transactions.** The provider call happens with no database transaction open, and the outcome is recorded afterwards in a short transaction guarded by the attempt's and payment's current state. A slow or hung provider cannot hold the SQLite writer, and a crash after the call is an ordinary, recoverable "unknown", not a lost lock.
4. **A stable provider idempotency key per attempt.** The key is stored before the call is made. A lookup, a restart replay or a duplicate dispatch all present the same key, so the provider can answer "already done" instead of charging again.
5. **Unknown outcomes are resolved only by the original provider.** A timeout or outage ends in `unknown`, not `failed`. The recovery worker looks the attempt up at the same provider with the stored key and applies whatever the provider says. The router is never consulted again for that payment, and there is no retry action in the UI or API for an unknown payment. If the provider never answers, the payment stays `unknown` and visible rather than being sent to a second provider and risking a double charge (measured for the `timeout_before_execution` and `outage` scenarios).
6. **Double-entry ledger.** A success posts one journal with a debit to the executing provider's clearing account and a credit to merchant payable, in the payment's currency and in integer minor units. Posted journals are immutable (database triggers reject updates and deletes), posting is keyed so a re-delivered completion adds nothing, and failed or canceled payments have no journal. `railvanta-api check` re-verifies balance, one-journal-per-success and reversal mirroring against any database, including restored backups.
7. **Reconciliation as evidence, not repair.** A run compares mock charges, payment state and posted journals for a window, records discrepancies with explanations, and never posts or changes anything. Late outcomes that contradict a terminal payment are stored for review instead of overwriting history.
8. **Exact money and honest UI.** Amounts are decimal strings of minor units end to end (including values above 2^53), currencies are never summed together, and the UI never shows success before the API confirms a terminal state. Simulated and seeded values are labelled.

## What was learned

- Making the unknown state first-class removed most special cases. Once "I do not know" is a status with a defined resolver, crash recovery and timeout handling are the same code path.
- Idempotency has to exist at every boundary: the client request, the outbox command, the provider call and the ledger posting. Fixing one layer only moves the duplicate to the next.
- Black-box tests that really kill and restart the API (`killApi()`) found failure modes that unit tests with fakes did not, and made the guarantees credible. Determinism (fixed mock scenarios, fixed seeds, no wall-clock behavior in the mock) is what makes those tests repeatable.
- Single-writer SQLite is a feature for a correctness demo and a ceiling for anything else. Bursts queue at the dispatcher (time-to-terminal reaches 1 to 2 s at concurrency 8 and 32 while acceptance stays in milliseconds), and there is an unconfigurable per-address rate limit that a measurement harness hits quickly.
- Measuring changed documents: the first measurement attempt tripped the rate limit and an early latency table was contaminated by the harness's own budget waits, so the final script reserves its request budget outside the timed regions and reads status from the database.
